# 신규 AI 에이전트용 블록 예제 제작 지시서 (v1, 2026-11-14, 만복)

- 지시자: 바로보기님. 작성: 만복(3AI).
- 목적: 새 에이전트가 **같은 3개 블록**을 만들어 **속도와 품질**을 측정한다. 결과로 수도권 밖 권역 확대 때 누구에게 맡길지 판단한다.
- 수신: 이 저장소(AI_idea)에서 작업하는 모든 신규·외부 에이전트. 에이전트마다 따로 폴더를 만들어 같은 과제를 한다.
- 병합하지 않는다. PR로 제출하고 3AI가 측정한다.

## 0. 공개 저장소 주의 (AI_idea는 공개)
- 이 과제의 블록은 **공공 정보로만** 만든다. 개인 위치·이동·사진, 키·토큰, 지도 서비스의 내부 결정은 넣지 않는다.
- 약관이 저장·복제를 제한하는 데이터(V-World 건물 외곽선 등)는 쓰지 않는다. 형상은 공식 기관 원문의 제원(치수, 층수, 구조)을 근거로 직접 모델링한다.

## 1. 먼저 읽을 것 (작업 전 필독, 읽지 않고 시작하면 무효)
순서대로 읽는다. **3번 가이드는 규격의 세부가 모두 여기 있으므로 전문을 읽는다.**
1. `README.md` (폴더 구조와 흐름)
2. `DIRECTIVE_NEW_AGENT_BLOCK_EXAMPLE_20261114.md` (이 문서)
3. **`GUIDE_3TEAM_BLOCK_TECH_20261114.md`** (3인 연합 제작 기술 가이드 원문 + 만복 보강, 약 23KB). 마지막 "만복 보강" 절에 이미 발견된 결함 5가지가 있다
4. `reference/11440_B50_마포중앙도서관/` (표준 예제 블록, v1.1 정정본)와 `reference/REFERENCE_NOTES.md`
5. `CHECKLIST.md` (측정기 번호와 같음)
6. `test_subjects.json` (만들 3개 주제)
7. `tools/check_example_block.py`, `tools/khronos_validate.mjs` (제출 전 직접 돌릴 측정기 두 가지)

### 읽기 확인 절차 (속도 측정의 시작 기준)
1. 가장 먼저 `timing/STARTED.md`에 **읽기 시작 시각(KST)**, 사용 모델·도구를 적어 커밋·푸시한다.
2. 위 문서를 읽고 `templates/READ_CONFIRM.md`의 10개 질문에 자기 말로 답한다. 이 파일을 `timing/READ_CONFIRM.md`로 커밋·푸시한다.
3. **READ_CONFIRM 커밋 시각이 제작 시작 기준**이다. 제작 속도는 이 시각부터 센다. 읽는 시간(`read_min`)은 따로 기록하고 속도 비교에는 합치지 않는다.
4. READ_CONFIRM의 답이 문서와 어긋나면 3AI가 반려하고 다시 쓰게 한다. 다시 쓰는 시간은 읽는 시간에 넣는다.
5. 문서끼리 충돌하는 곳을 찾으면 숨기지 말고 READ_CONFIRM 마지막 칸에 적는다. 충돌 시 우선순위는 **이 지시서 > 가이드 본문 > 가이드의 만복 보강 중 실측 사실**이다.

## 2. 만들 것
`block_example/<에이전트이름>_block/` 폴더 안에 블록 3개와 시간 기록.

```
block_example/<에이전트이름>_block/
  26170_B26_대한성공회부산주교좌성당/   (4종 파일)
  26170_B36_동구국민체육센터/           (4종 파일)
  26170_B44_초량어린이도서관/           (4종 파일)
  reports/                          (측정기가 만드는 <폴더명>_check.json)
  evidence/                         (렌더 캡처 {슬롯}_front.png, _bird.png, _eye.png, 1400×980)
  timing/
    STARTED.md                      (읽기 시작 선언, §1)
    READ_CONFIRM.md                 (읽기 확인 10문항, 제작 시작 기준)
    timing_B26.json  timing_B36.json  timing_B44.json
  REPORT.md                          (templates/REPORT.md 양식)
```

블록 폴더마다 **파일 4종만** 넣는다. 스크립트·소스·측정 리포트·캡처는 블록 폴더 밖(`reports/`, `evidence/`)에 둔다.

| 파일 | 내용 |
|---|---|
| `model_lod3.gltf` | 근거리 모델. glTF 2.0, **버퍼 내장(data URI)**, 삼각형 10,000~14,000, 재질 11종, UV uint16 normalized |
| `model_lod2.gltf` | 원거리 모델. 삼각형 1,200~1,800 |
| `texture_atlas.webp` | 1024×1024 단일 아틀라스, 100KB 이하 |
| `block_manifest.json` | 제원·출처·좌표·예산. 필수 키는 CHECKLIST M01 |

### 파일 포맷 결정
- **표준은 `.gltf`(버퍼 내장) + `block_manifest.json`**이다. 3AI의 점검·편입 도구가 이 형식에 맞춰져 있고, 같은 형식이어야 속도·품질을 공평하게 비교할 수 있다.
- `.glb`로 작업하는 도구라면 마지막에 위 `.gltf` 형식으로 변환해서 제출한다. 변환 시간도 제작 시간에 포함한다. **변환 도구가 접근자 `min`/`max`를 잘못 쓰는 경우가 있으니** Q15·Khronos 검사로 반드시 확인한다.

## 3. 품질 기준 (숫자, 측정기 `tools/check_example_block.py` 36항목 + Khronos 검증기)
| 번호 | 기준 |
|---|---|
| Q01/Q02 | LOD3 삼각형 10,000~14,000, LOD2 1,200~1,800 |
| Q03/Q04 | LOD3 768,000B 이하, LOD2 71,680B 이하 |
| Q05 | 접지: LOD3·LOD2 모두 최저점 Y = 0.000(허용 ±0.005). **선언값이 아니라 실제 정점 데이터로 잰다.** 바닥판을 깔지 않는다 |
| Q06 | 인덱스 uint16, 법선(NORMAL) 버퍼 없음 |
| Q07 | 텍스처 참조는 `texture_atlas.webp` 하나, 버퍼 내장 |
| Q08/Q09/Q10 | 텍스처 1024×1024 WebP 102,400B 이하, 패키지 972,800B 이하 |
| Q11 | 재질 정확히 11종(wall, trim, glass, roof, stone, ground, metal, wood, accent, plaque, misc) |
| Q12 | `TEXCOORD_0`가 uint16 normalized |
| Q13 | 모든 노드에 `name` |
| Q14 | 앵커 노드: `night_light_*` 4개, `hotspot_*` 5개 (LOD3) |
| **Q15** | **접근자 `min`/`max` 선언이 실제 데이터와 일치**(뷰어 경계 상자·컬링에 쓰임) |
| **Q16** | **`scene.nodes`가 유효**(범위 밖 인덱스 0, 장면에 연결 안 된 노드 0) |
| M01~M09 | 매니페스트 필수 키, 좌표, 공식 출처 1건 이상(참조 4건 이상), 열람 시각(KST), 개인정보·키 없음, 슬롯 일치, V-World 풋프린트 참조·공공누리 오표기 없음, 뷰어 규약(lod_switch 200, ground snap, ASL 필드 없음, 실행코드 미포함) |
| **Khronos** | `node tools/khronos_validate.mjs <gltf>` 결과가 **WebP MIME 확장 미선언 2건 외 오류 0** (아래 표 3번 편차는 허용, 그 외는 불합격) |

시각 품질은 제미나이가 8항목 체크리스트로 본다(CHECKLIST 3절). 에이전트는 제출 전 자기 눈으로 같은 항목을 먼저 확인한다.

## 4. 출처와 사실 규칙
1. 건축 제원(높이, 층수, 치수, 구조, 준공 연도)은 **공공·공식 출처**(go.kr, or.kr 등)에서 가져온다. 위키·블로그·지도 앱은 보조로만 쓰고, 이것만 근거로 삼지 않는다.
2. 출처마다 URL과 **KST 열람 시각**을 매니페스트에 적는다. 열람하지 못한 것은 "미확인"이라고 쓰고 값을 지어내지 않는다.
3. `test_subjects.json`의 좌표는 **시작점일 뿐 정확하지 않다**(반올림된 값). 공식 출처로 확인해 매니페스트 좌표를 바로잡는다.
4. 공공누리 유형을 쓸 때는 정확히 쓴다. 1유형=출처표시, 2유형=**비영리 전용**, 3유형=변경금지, 4유형=비영리+변경금지. OSM을 쓰면 ODbL 1.0 출처 문구를 넣는다.
5. 제3자 이미지·사진 픽셀을 텍스처에 넣지 않는다. 텍스처는 직접 생성한다.
6. 확신이 없는 수치는 `review_notes`에 "추정"이라고 쓴다.

## 5. 시간 기록 (이 과제의 핵심 측정)
속도는 **말이 아니라 기록으로** 본다. 두 가지를 같이 남긴다.

1. **시작 선언 커밋**: 읽기를 시작하기 **전에** `timing/STARTED.md`를 먼저 커밋·푸시한다(§1). **제작 시작 기준은 READ_CONFIRM 커밋 시각**이다.
2. **블록별 `timing_<슬롯>.json`**: `templates/timing.json` 양식. 블록 시작·종료 시각, 실제 작업 시간, 재시도 횟수, 단계별 소요(자료 조사 / 모델링 / 최적화 / 검증), 사람 개입 횟수, 시작·종료 커밋 해시를 적는다.
3. 3AI는 **커밋 시각으로 교차 확인**한다. 자기 보고 시각과 커밋 시각이 크게 어긋나면 커밋 시각을 쓴다.
4. 세 블록은 **연속으로** 만들어도 되고 병렬로 만들어도 된다. 병렬이면 timing에 "병렬"이라고 적는다.
5. 시간은 세 가지로 나눠 적는다: `read_min`(읽기, STARTED→READ_CONFIRM), `wall_clock_min`(제작, READ_CONFIRM→블록 마지막 커밋), `active_min`(실제 작업). 속도 비교는 제작 시간(`wall_clock_min`)으로 한다.
6. 토큰·비용 사용량은 알 수 있으면 `tokens_self_reported`에 적는다(선택, 비교에 쓰지 않고 참고만).

## 6. 제출
1. `block_example/<에이전트이름>_block/`를 새 브랜치에 올리고 PR을 연다. 제목: `[블록예제] <에이전트이름> 3블록 (B26·B36·B44)`.
2. 제출 전 블록마다 측정기와 Khronos 검증기를 돌린다. 리포트는 자동으로 `<에이전트이름>_block/reports/`에 생긴다.
   `python tools/check_example_block.py block_example/<에이전트이름>_block/26170_B26_대한성공회부산주교좌성당 --timing block_example/<에이전트이름>_block/timing/timing_B26.json`
   `node tools/khronos_validate.mjs block_example/<에이전트이름>_block/26170_B26_대한성공회부산주교좌성당/model_lod3.gltf` (LOD2도 같게)
3. `REPORT.md`에 측정기 결과 요약, 막혔던 점, 사람 개입, 다음에 더 잘할 점을 적는다.
4. 합격하지 못한 항목이 있으면 숨기지 않고 REPORT에 적는다. 자체 "PASS" 표기는 3AI가 다시 측정하므로 의미가 없다.

## 7. 3AI의 평가 (참고)
- **품질**: 측정기 통과율 + 제미나이 시각 8항목 + 만복의 출처 표본 대조(수치 3개를 원문과 직접 비교).
- **속도**: 블록당 걸린 시간(평균, 최소, 최대)을 품질과 **따로** 보고한다. 점수로 합치지 않는다.
- **확대 판단**: 수도권 밖 권역에 맡기려면 세 블록 모두 측정기 전 항목 통과, 시각 평균 6/8 이상, 출처 대조 오류 0건이 필요하다. 속도 기준은 피망 삼총사의 같은 과제 기록과 비교해 정한다 (?). 3AI는 Khronos 검증기와 측정기를 모두 재실행한다.

## 8. 만복 추가 의견 (바로보기님이 말씀하신 것 외에 공정한 비교와 확대 판단에 필요해서 넣음)
1. **격리**: 에이전트끼리 결과를 보지 않는다. 각자 다른 브랜치에서 작업하고, 다른 에이전트 폴더를 열지 않는다. 같은 과제의 복사를 막기 위해서다.
2. **출발선 동일**: 입력은 `reference/`, `CHECKLIST.md`, `test_subjects.json`, 측정기뿐이다. 이 밖의 정답 자료(다른 블록의 결과물)는 받지 않는다.
3. **씨앗 정보는 미확인**: `test_subjects.json`의 설명·좌표는 확인되지 않은 초안이다. 공식 출처와 다르면 고쳐야 하고, 그 차이를 REPORT의 "씨앗과 다르게 확인한 것" 표에 적는다. 이 표가 비어 있으면 검증을 하지 않았다는 뜻으로 본다. (속도뿐 아니라 **정확성 습관**을 보기 위함)
4. **처음 통과까지의 시간과 수정 횟수**: 최종 통과 시간 말고 `time_to_first_pass_min`(측정기를 처음 전부 통과한 시점)과 `validation_loops`(측정기를 돌린 횟수)를 적는다. 한 번에 통과하는 에이전트와 고쳐 가며 통과하는 에이전트는 확대 때 비용이 다르다.
5. **한도와 하루 처리량**: 에이전트의 사용 한도 체계(시간당·일일·리셋 시각)와 작업 중 중단·재개 횟수와 사유를 적는다. 삼총사가 일일 토큰이라 낮에 끝나면 새벽에야 재개되는 것처럼, 확대 계획은 **하루에 몇 블록이 나오는가**로 세운다. 이 수치는 `capacity_self_estimate`에 추정으로 적고, 3AI가 실제 PR 시각으로 다시 계산한다.
6. **비용·도구 선언**: 쓴 모델·도구·외부 서비스를 모두 적는다. 유료 API를 쓰면 반드시 적는다(3AI 원칙: 비용 0원 구조 우선, 유료는 사전 보고).
7. **렌더 증거**: 블록 3개 각각에 대해 정면·조감·눈높이 렌더 캡처 3장을 `<에이전트이름>_block/evidence/<슬롯>_front.png`, `_bird.png`, `_eye.png`(1400×980)로 남긴다(블록 폴더 안이 아니라 evidence 폴더). 카메라는 가이드 §3.6의 산출 방식을 따른다. 뷰어에서 실제로 열린다는 증거이자 제미나이 시각 점검 자료다.
8. **스타일 일관성**: 서로 다른 에이전트의 블록이 한 지도에 섞여도 어색하지 않아야 한다. 참조 블록의 재질 개수(약 13개), 바닥 처리, 색 계열을 기준으로 삼는다. 제미나이 시각 체크리스트에 "참조와 같은 지도에 놓았을 때 이질감" 항목이 있다.
9. **재현 정보**: 사용한 도구 버전, 난수 시드, 생성 방식(직접 코드 / 절차적 생성 / 수작업 편집)을 `generation`에 적는다. 재작업이 필요할 때 같은 방식으로 다시 만들 수 있어야 한다.
10. **정직한 미완 보고를 우대**: 못 한 항목, 못 구한 출처, 못 맞춘 기준을 솔직히 적으면 감점하지 않는다. 지어낸 수치와 가짜 PASS는 가장 크게 감점한다(키링이 사례: 교체했다고 보고했으나 실제로는 그대로였던 일).
11. **편입 호환**: 3AI의 점검기(`repo_watch.py`)가 PR 본문과 매니페스트를 읽어 자동 점검한다. PR 본문에 삼각형 수·용량·접지·출처 URL을 표로 적어 주면 자동 점검이 막히지 않는다(참조 PR 형식은 `reference/REFERENCE_NOTES.md`). 3인 연합 가이드가 요구하는 `validate_block.py` 실행 로그는 이 시험에서는 `reports/` 리포트로 대신한다.
12. **자체 점수를 합격으로 쓰지 않는다**: 측정기·검증기 통과는 최소선이다. 최종 판정은 제미나이의 사용자 입장 시각 점검과 만복의 출처 대조다..

## 9. 3인 연합의 후속 정정 (참고)
- 3인 연합(피망)이 PR #1280 회신으로 알린 것: 쿼카·피클·피망 모두 V-World 건물 풋프린트 미사용(자기 보고), 쿼카는 팔달 41115 3차 5선(#1281~#1285)부터 `license_note`를 사용/미사용 분리 형식으로 정정, 기존 PR 일괄 수정은 3AI 안내 뒤에 한다.
