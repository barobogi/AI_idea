## 3줄 요약
1. 세 후보 모두 서울(37.5665N, 126.9780E) 2026-12-06 세 시각에서 NOAA 기준 대비 고도·방위 오차가 0.3° 미만으로, 시각적 시간대 조명 용도 기준으론 전부 유효 범위다 (방위 최대 오차 0.16°, 고도 최대 오차 0.30°).
2. suncalc 2.1.4가 오차·크기·관리상태 모두에서 가장 균형(최대 오차 0.08°, gzip 5.3KB, 2026-11-10 배포), suncalc3는 굴절 미보정이라 저고도에서 최대 0.26° 오차, sun-position은 실행 중 CDN에서 타임존 데이터를 내려받는 네트워크 의존이 있다.
3. 특이점 3건: ① sun-position의 getAzimuth()는 같은 인스턴스에서 getElevation()를 먼저 호출하지 않으면 NaN을 반환(실측 확인) ② suncalc·suncalc3의 package.json에는 license 필드가 없고 LICENSE 파일 텍스트(BSD 2-clause 형식)로만 확인 가능 ③ 기준값은 NOAA 계산기 웹 UI 수기 입력이 아니라 NOAA 계산기 자체 JS(main.js)를 로컬 실행해 산출했다.

## 사용한 명령·버전 (그대로)

- Node v20.18.1 (로컬 샌드박스), npm 레지스트리 설치본 그대로 사용.
- 기준값: `NOAA.calcAzEl(NOAA.calcTimeJulianCent(JD), 540|720|1020분, 37.5665, 126.9780, 9)` — JD는 UTC 인스턴트 기준 (`ms/86400000 + 2440588`). localtime은 자정부터의 분, zone=9(KST).
- suncalc 2.1.4: `SunCalc.getPosition(new Date('2026-12-06T00:00:00Z'), 37.5665, 126.9780)` → azimuth(도, 북 기준 시계방향)·altitude(도, 굴절 보정 포함). CJS/ESM 엔트리 결과 동일 확인.
- suncalc3 2.0.5: `SunCalc.getPosition(date, lat, lng)` → azimuth는 **라디안**이므로 `deg = azimuth*180/π` 변환, altitude는 라디안(굴절 미보정).
- sun-position 0.1.2: `TZ=Asia/Seoul` 환경에서 `new SunPosition(37.5665, 126.9780, new Date(2026,11,6,9,0))` 후 `getElevation()` → `getAzimuth()` 순서로 호출(README 예시 방식).

## 라이브러리별 특이점 (실측)

- **suncalc 2.1.4**: v2 계열로 Meeus 고정식 + ΔT(Espenak & Meeus 다항식) 적용. azimuth 반환 단위가 v1(라디안, 남쪽 기준)에서 도(북 기준)로 바뀐 것으로 보이므로 v1.x에서 업그레이드 시 단위 확인 필요 (소스 주석 기준).
- **suncalc3 2.0.5**: suncalc v1 포크로 굴절 보정 없음. 17:00의 고도 오차 −0.255°는 1.8° 고도에서의 굴절량(≈0.25°)과 일치 — 알고리즘 오류가 아니라 보정 유무 차이. 2년 이상 무갱신.
- **sun-position 0.1.2**: ① 태양 적위선을 단순식 `23.45·sin(360/365·(일수−81))`로 계산 ② 표준자오선/타임존 판정을 위해 실행 중 `cdn.jsdelivr.net`에서 geo-tz 데이터를 fetch — 오프라인·차단 환경에서 동작 보장 안 됨 (타임�zone 조회 실패 시 경도/15° 근사로 폴백) ③ getAzimuth()가 getElevation()에 의존 (먼저 호출 안 하면 NaN → 실측에서 null로 반환) ④ dist 번들에 소스맵 포함(총량 큼).
